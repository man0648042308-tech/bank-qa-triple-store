# Day37 当天学习总结

## 1. 今日核心

今天学习了怎样把 Elasticsearch、Redis、Neo4j 和 Python 业务规则组合成银行智能问答系统。最重要的收获不是记住四个名词，而是理解每个组件的责任边界：

- Elasticsearch：从大量产品文字中找到相关候选，支持BM25评分、结构化过滤和高亮。
- Neo4j：表达客户、风险等级、资产与产品之间的图关系。
- Redis：缓存可以重建的临时问答结果，减少重复计算。
- Python：执行确定性的金融安全规则，并控制完整处理顺序。
- LangChain思路：用统一输入输出接口组合各步骤，但不能替代业务规则。

## 2. 练习五的知识链

输入四个可选参数：

```text
keyword、min_price、max_price、category
```

程序先分别建立：

```python
must_clauses = []
filter_clauses = []
```

关键词查询加入 `must`，因为它会影响相关度；价格和品类加入 `filter`，因为它们只需要做“满足/不满足”的判断。价格边界使用 `is not None`，这样 `0` 不会因布尔值为假而被遗漏。

搜索响应的两块重要内容是：

- `_source`：原始文档字段；
- `highlight`：带 `<em>` 标签的命中片段。

没有高亮时必须回退到 `_source["name"]`，否则代码可能因为缺少键而报错。

## 3. 完整银行问答链

```text
用户问题
→ Neo4j读取最新客户画像
→ 分类为推荐、产品事实或领域外；领域外立即拒答
→ 用客户编号、画像指纹、产品目录指纹、规范化问题摘要和数据版本构造缓存键
→ Redis命中当前画像对应的结果则返回
→ 未命中才执行Elasticsearch文本召回与Neo4j关系召回
→ RRF融合两路名次
→ 推荐问题执行状态、风险和金额硬过滤
→ 事实问题定位明确产品并回答特点/风险/起投；推荐问题生成合规候选回答
→ 写入带TTL的Redis
```

先读取画像看似多了一次查询，却防止风险等级或可用金额变化后仍命中旧推荐。缓存不是事实来源；画像指纹和产品目录指纹用于隔离旧答案，数据版本用于整体版本隔离，TTL只负责最终过期。

## 4. 金融安全理解

搜索引擎负责“相关”，业务规则负责“允许”。下面三条均是不可放宽的硬规则：

1. 产品必须在售；
2. 客户风险承受能力必须覆盖产品风险；
3. 客户可用金额必须达到起投金额。

不能只把这些规则写进提示词，因为模型输出具有概率性；确定性判断必须由代码和测试完成。

## 5. 工程方法

- 把查询体构造与网络调用分离，便于不启动数据库也能测试合同。
- 把离线逻辑测试与真实集成验证分开，便于定位到底是代码错误还是环境错误。
- 配置与源码分开，避免把地址、密码和密钥写入提交包。
- 三库只绑定VM回环地址，Windows经SSH隧道连接本地`127.0.0.1`端口。
- FastAPI三个业务端点验证`X-API-Key`，密钥只放当前PowerShell的`DAY37_API_KEY`。
- Neo4j使用参数化Cypher，不把客户输入直接拼接到查询字符串。
- 所有最终回答都应保存来源；没有证据时应拒绝猜测。
- “安心存款风险是多少”是事实问答；“我适合买什么”是推荐；“今天天气如何”是无关问题，三者不能共用同一种产品清单回答。
