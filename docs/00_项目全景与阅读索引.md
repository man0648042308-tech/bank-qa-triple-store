# 项目全景与阅读索引

## 1. 一句话理解项目

系统把“客户问题”转换为“可审核的问答过程”：先读取最新客户画像并分类；领域外直接拒答，其余问题安全构造缓存键；缓存未命中才进行ES/Neo4j检索与RRF，事实问题定位明确产品，推荐问题再执行硬过滤，最后生成可追溯回答。

## 2. 先建立全景，不要从第一行硬啃

```text
输入：customer_id + question
              |
              v
      Neo4j读取最新Customer
              |
              v
 classify_query(推荐 / 产品事实 / 领域外)
       |                  |
       |领域外            |推荐或事实
       v                  v
  空来源、空产品ID拒答   build_cache_key(
                        客户 + 画像指纹 + 目录指纹
                        + 问题摘要 + 数据版本)
              |
              v
          Redis缓存
       命中 /      \ 未命中
           /        \
       返回当前画像键下结果   ES文本检索 + Neo4j关系检索
                         |
                         v
                      RRF融合
                         |
                         v
              事实：定位明确产品
              推荐：状态、风险、金额硬过滤
                         |
                         v
                    事实回答 / 推荐回答
                         |
                         v
                 Redis SET + TTL
```

这里有两个不能混淆的层次：

- **召回层**：尽量把可能相关的产品找出来，允许候选较多。
- **准入层**：决定候选是否允许推荐，必须严格、可测试、不可由 LLM 猜测。
- **问答层**：事实查询回答产品属性；推荐查询才应用个性化准入；无关查询不召回或不输出产品。

## 4. 分层阅读顺序

### 现在必看

1. `README.md`：知道入口。
2. `exercise05/query_builder.py`：今天最小语法核心。
3. `tests/test_exercise05_query.py`：知道需求合同到底写在哪里。
4. `models.py` 和 `sample_data.py`：先认清数据。
5. `business_rules.py`：先守住金融安全。
6. `pipeline.py`：最后把各组件串起来。
7. `tests/test_pipeline.py`：用案例确认理解。

### 稍后再看

1. `cache.py`：先理解键和TTL，再关心真实Redis客户端。
2. `elasticsearch_retriever.py`、`neo4j_repository.py`：离线版跑通后读外部适配。
3. `api.py`：命令行主链路懂了再学习HTTP与API Key鉴权。
4. `rrf.py`：当存在两路以上排名时再深入公式。

### 第一遍可以跳过

- `uv.lock`：机器生成的依赖锁文件，不适合逐行读。
- `.venv`：虚拟环境依赖，不属于项目源码。
- `output/*.pdf`、`output/*.zip`：提交产物，不是实现逻辑。
- `tmp`、缓存目录：临时资产。
- Compose中的底层镜像实现：第一遍只理解服务、端口、卷和网络。

跳过不代表永远不学，而是避免第一次被低收益细节淹没。

## 5. 黄金执行路径

先不启数据库：

```text
PowerShell
 -> uv run python -m day37_bank_qa.main --offline ...
 -> main解析参数
 -> 构建离线BankQAPipeline
 -> 读取最新固定客户画像
 -> classify_query区分推荐/事实/领域外
 -> 领域外直接拒答；其余问题构造画像与目录版本缓存键
 -> 未命中后执行两路离线检索并RRF融合
 -> 推荐执行filter_eligible_products；事实定位明确产品
 -> DeterministicAnswerGenerator生成对应回答并写缓存
 -> 打印answer、sources、cache状态
```

再运行真实三库：

```text
PowerShell脚本
 -> SSH进入VM
 -> docker compose启动day37隔离容器
 -> 初始化ES索引和Neo4j数据
 -> VM服务仅绑定127.0.0.1
 -> scripts/06启动Windows本地SSH隧道
 -> Windows Python连接127.0.0.1本地端口
 -> tests/verify_full.py
 -> 独立QA完整回归通过后才生成evidence/验收记录.md
```

## 6. 术语表

| 术语 | 初学者解释 |
|---|---|
| 索引 index | Elasticsearch里一组同类文档的集合 |
| 文档 document | 放进索引的一条JSON记录 |
| mapping | 字段名、类型和索引方式的合同 |
| 倒排索引 | 从“词”反向找到包含它的文档 |
| BM25 | 根据词频、文档长度和词的稀有程度计算相关性 |
| `must` | 必须匹配且通常参与相关度评分的子查询 |
| `filter` | 只做是否满足判断、不参与相关度评分的条件 |
| `_source` | Elasticsearch保存的原始文档内容 |
| highlight | 搜索响应中带标签的命中片段 |
| Redis key | 找到缓存值的唯一名称 |
| TTL | 缓存键剩余生存时间 |
| cache hit | 缓存中已经有结果 |
| cache miss | 缓存没有结果，需要重新计算 |
| 画像指纹 | 由风险等级、可用金额等影响答案的画像字段生成的稳定标识 |
| 节点 | Neo4j中的实体，如客户或产品 |
| 关系 | 节点之间的有方向连接 |
| Cypher | Neo4j的图查询语言 |
| 参数化查询 | 查询语句与用户值分开传递，降低注入风险 |
| RRF | 依据各列表中的名次融合多个排序 |
| LangChain Runnable | 具有统一调用接口、可组合成处理链的组件抽象 |
| pipeline | 输入依次经过多个步骤形成输出的处理链 |
| 硬过滤 | 必须严格满足、不能让模型自行放宽的规则 |
| 事实问答 | 回答产品特点、风险、起投等客观字段，不等于推荐 |
| 推荐问答 | 结合客户画像并经过硬过滤后给出适配候选 |
| 拒答门 | 对无关领域或证据不足问题返回空产品结果，不强行推荐 |
| SSH隧道 | 把本机端口经加密SSH连接转发到VM回环服务 |
| `X-API-Key` | FastAPI每个端点都要求的请求头；值来自当前进程环境变量 |

## 7. 本地课程与前序工程复用索引

本项目不是脱离课程资料重新编造，而是先核对原题，再复用已经验证过的前序能力。下表说明“从哪里来、复用了什么、为什么没有原样复制”。

| 分级 | 本地来源 | 本项目实际用途 | 为什么不原样复制 |
|---|---|---|---|
| 直接合同 | `课程私有仓库 | 确定学习总结、两组面试题、练习五和银行问答四项必交内容 | 原题只规定结果，不包含可验收工程 |
| 直接合同 | `课程私有仓库 | 固定练习五的四个可选参数、`must/filter`、前10条、总数和高亮 | 参考答案主要负责打印，缺少稳定数据、返回模型和自动测试 |
| 改造复用 | `课程私有仓库 | 设计Redis键、JSON缓存、TTL和第二次命中验证 | 示例没有充分隔离不同客户和数据版本 |
| 架构参考 | `课程私有仓库 1.x + Neo4j + Elasticsearch + Redis 混合检索架构.md` | 确定缓存、画像、检索、融合、生成的整体顺序 | 文档中的部分API、固定地址、初始化和异常处理不能直接运行 |
| 数据参考 | `课程私有仓库 | 参考虚构客户、银行产品和问句形式 | 该工程没有声明ES、Redis、Neo4j三库依赖，不能作为Day37直接起点 |
| 图谱参考 | `课程私有仓库 | 参考客户、产品、分类、知识节点和参数化Cypher | Day37必须使用独立标签和`dataset_id='day37'`，不能混入旧图数据 |
| 代码复用 | `./Day35_Day36_GraphRAG_Homework\src\day3536_homework` | 复用数据模型、硬业务规则、RRF融合和Neo4j适配器的设计思想 | Day35/36主线是GraphRAG与Milvus；Day37必须增加ES练习五、Redis缓存和问答接口 |

### 本次明确没有复用的内容

- 没有直接启动或修改Day34～36旧容器和旧数据卷。
- 没有把Milvus加入Day37必做主链，因为原题的最低范围是ES、Redis、Neo4j与LangChain问答闭环。
- 没有安装课程目录中的IK 8.6.2插件，因为本项目ES服务器使用8.18.0、Python客户端锁定8.18.1；IK插件必须与服务器精确版本匹配。
- 没有复制任何真实个人数据、`.env`、密码、Token或API Key。

## 8. 已验证、推断和未知

### 已验证的课程合同

- Day37原题确实包含学习总结、ES/Redis各10题、练习五和银行问答项目。
- 练习五要求四个可选参数、`must`、`filter`、高亮、前10条和总命中数。
- 本项目固定采用Windows写代码、虚拟机Docker运行数据库的边界。
- 2026-08-31当前源码的离线验证：47项pytest通过，Ruff通过，compileall通过。
- 离线Evaluation Harness的4条硬案例全部通过，`passed=4`、`total=4`、`score=1.0`。

### 根据源码结构推断的设计意图

- 将查询体构造与真实ES调用分离，是为了让查询合同可离线测试。
- 保留离线pipeline，是为了把业务逻辑错误与数据库连接错误分开定位。
- 将回答生成器做成独立组件，是为了未来替换模型而不重写检索和安全规则。

### 完成真实运行后才能确认

- 当前三个容器和SSH隧道的健康状态。
- Elasticsearch 8.18.0首次镜像拉取用时。
- API无密钥/错误密钥401、正确密钥200的现场结果。
- 无关问题拒答、事实问答、推荐与画像变化缓存隔离的现场输出。

上述现场事实以本次终端输出为准；如果最终验收流程随后生成并复核了`evidence/验收记录.md`，它可以作为归档证据。文档不提前把计划写成事实。
